Clever Sandbox Events API Data Drift Engine

Scheduled, semi-autonomous CSV drift for Clever sandbox districts — so application partners have a live Events API stream to build against instead of a static roster.

Sandbox-only, hard-enforced Fixed weekly cadence CSV-over-SFTP 10% guardrail v0.3.0

github.com/dmcgeary76/event-api-sim

What this is, and why

Clever sandbox districts are set up for application partners to test workflows built on Clever's Events API — but the roster data is static once loaded, so there's no ongoing stream of created / updated / deleted events for a partner to actually observe. This engine keeps a working copy of one sandbox district's CSV roster stack, makes a small, bounded set of realistic edits on a fixed weekly pattern, and re-syncs it over the district's existing SFTP pipeline. Clever's own ingestion diffs the new export against the last one and emits the corresponding Events API records — the engine never calls Clever's API directly.

It deliberately does not have a per-district volume knob or a per-partner change profile: the same cadence and magnitude apply to every configured sandbox district, because partners are told to expect activity on a known, predictable schedule.

The fixed weekly cadence

DayBucket(s)What happens
Mondaysmall_dailyA handful of minor field edits — contact email/phone tweaks, student middle-name/email edits.
Tuesdaysmall_daily + big_studentSmall daily, plus ~4 students moved between sections, a few new guardian contacts, and a couple of contact removals.
Wednesdaysmall_dailySmall daily only.
Thursdaysmall_daily + big_studentSame shape as Tuesday.
Fridaysmall_daily + big_teacherSmall daily, plus co-teacher swaps, a primary-teacher reassignment, and one brand-new teacher added.
Saturday / Sunday—Skipped entirely. No drift runs on weekends.

Big buckets stack on top of the small daily bucket — they never replace it. Magnitudes are hard-coded constants in cadence.py, not configuration.

Event types produced

Corrected 2026-08-03: the project brief (§3) incorrectly assumed contacts had their own distinct event types (contacts.created/contacts.updated/contacts.deleted). They do not exist on Clever's real Events API. Verified against Clever's live dev docs (Events API, Contacts & guardians): in API v3.x, contacts, students, teachers, staff, and district admins are all users objects on the wire — only users.created/users.updated/users.deleted and sections.* are real events. Role is carried in the object's own roles node, not the event name. The table below shows both the real wire event and the role label this engine's reports use for readability.

Wire event (real)RoleProduced by

users.updatedContactsSmall daily contact field edits (email, phone, phone type)
users.deletedContactsBig-student guardian removals (never orphans a student's last contact)
users.updatedStudentsSmall daily student field edits (middle name, student email)

Resolved 2026-08-05 -- contacts are rows on students.csv

This was carried for weeks as a KNOWN BLOCKER, and it was a real one. It has now been verified and fixed, not assumed away. Authority: Clever's official SFTP Instructions, v2.1.1 (Dec 2025), confirmed by David on 2026-08-05 against the standard SFTP allowable-fields list. Coverage on contacts from Clever's internal answer bot was thin, so the current PDF is treated as authoritative over general memory.

  • There is no standalone contacts.csv. Guardian contacts are columns on students.csv: Contact relationship, Contact type, Contact name, Contact phone, Contact phone type, Contact email, Contact sis id -- unsuffixed and singular.
  • Multiple contacts are multiple rows for the same Student id, quoting v2.1.1: "In order to provide multiple parent/guardian contacts, you may create multiple rows for a single student with different contact information." Maximum 5 per student, no custom mappings.
  • There is no contact_name_2 / contact_email_2 convention -- those headers are not real. Do not conflate this with sections.csv, which in the same spec genuinely does use Teacher 2 id..Teacher 10 id for co-teachers. Sections widen; contacts repeat.
  • Contact sis id governs identity stability. With one, a contact keeps its Clever id across phone/email/name changes; without one, Clever derives the id from name+email (else name+phone, else name+type+relationship+phone type), so an email edit changes the identity key itself and reads as delete-then-create rather than users.updated. When IDEA Public Schools added contact_sis_id, Clever's PE team confirmed every existing contact id would change -- there is no id-preservation path once the identity basis shifts.
  • Engine response: every contact it creates gets a minted, permanent Contact sis id that is never edited; students.csv's key is now (Student id, Contact sis id); a student with no contacts keeps one blank-contact row, and their first guardian fills it in place (a CSV UPDATE that is a contact CREATE to Clever); student-level edits fan out across sibling rows; counts() reports distinct students plus a derived contacts count; the guardrail attributes contact-row deletes to contacts, not students. All row expansion goes through one function, schema.expand_contact_rows, so a future spec correction is a one-function change.
  • Partner-facing footnote: on the SIS-managed auto-sync side, contact.sis_id is only honored for Infinite Campus, IC OneRoster API, Skyward, and Skyward API. Irrelevant to an SFTP sandbox, but it matters if a partner compares sandbox behaviour to a real auto-synced district.

Safety model

Username allowlist, not hostname

sftp.clever.com is shared infrastructure across many districts, so the hostname proves nothing about whether a target is a sandbox. The SFTP username identifies the district, and the engine hard-fails if the resolved username isn't listed in config/districts.yml.

Data fingerprint, strength-checked + scale sanity

The loaded stack must contain a configured substring (e.g. tulsaschools-replica.org) in its own data — and the fingerprint itself must be ≥8 characters, contain a ., and contain a recognised sandbox marker (replica/sandbox/dev/etc.) before it's trusted as a check at all. Record counts must also stay within 25% of a recorded baseline, checked every run.

10% / 2% deletion guardrail

Clever's real 10% pause-for-review threshold is enforced as a hard block before anything is written. This engine's own stricter 2% ceiling is enforced as a warning. Matched enrollment moves are netted out of the count; unexplained row loss versus the last real push (e.g. a truncated export) is caught.

Dry-run by default

run and seed never open an SFTP connection without an explicit --live flag — no configuration path changes that default. Dry-run output is pruned to the 5 most recent directories per district.

One run per district at a time

An exclusive file lock on state/<district>/.lock is held for the whole of a run; a second overlapping run exits immediately with code 3 instead of racing the first and potentially minting colliding IDs for two different students.

Timezone-aware cadence

Each district's own timezone (default America/Chicago) decides which weekday it is for cadence purposes — never the host machine's or UTC's — so a run near a day boundary can't silently skip a whole day's bucket.

Using the tool

Run locally

python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env   # fill in the SFTP password

drift-engine schedule
drift-engine run          # dry run — no SFTP connection at all
drift-engine run --live   # push for real

Full details in the repository README, the CSV contract in SCHEMA.md, and operational guidance in RUNBOOK.md.

Changelog

Mirrors CHANGELOG.md. Newest first.

2026-08-07

— v0.3.0: Teacher attrition

  • Added: the Friday big_teacher bucket now removes one teacher for every new one it adds, always from a different school than the one that gained a teacher that run. Resolves the "teacher population has no attrition" known limitation flagged since v0.1.0 (unchecked, it would have breached safety.MAX_SCALE_DRIFT in roughly 7 years). Uses the existing EventType.USERS_DELETED / EventSubject.TEACHER -- no new event type needed. A teacher is only ever removed once every sections.csv row referencing them has somewhere else to point: sections where they're the primary teacher are reassigned to another same-school teacher first, and sections where they're a co-teacher have that slot cleared -- the same integrity discipline the 0.2.0 contacts rework required, so a removal can never leave a section pointing at a deleted teacher id. Skips the removal for a run rather than forcing it through if no safe candidate exists in another school. Verified with a 200-seed sweep plus new targeted unit tests in tests/test_selection.py.
2026-07-30

— v0.1.0: Initial release

  • Core engine: schema, models, safety, config, csvstack, cadence, selection, content, seed, guardrail, sftp_push, audit, runner, and cli modules, implementing the full per-run flow from the project brief.
  • Fixed weekly cadence: small daily edits every weekday; big student changes Tue/Thu; big teacher changes Friday; weekends skipped — magnitudes hard-coded, not configurable per district.
  • Six event categories: contacts.created/updated/deleted, sections.updated, users.updated, and teachers.created (added beyond the brief's original five for the Friday new-teacher sub-bucket).
  • Safety model: host + SFTP username allowlist (not hostname), a strength-validated data fingerprint, scale sanity, and an advisory production-marker tripwire — none of which are ever caught or downgraded, and a SafetyViolation is always audited before it propagates.
  • Concurrency: an exclusive per-district file lock prevents two overlapping runs from minting colliding IDs and corrupting each other's edits.
  • Timezone-aware cadence: each district's own configured timezone (default America/Chicago) decides which weekday it is, not the host machine's or UTC's.
  • Guardrail: Clever's real 10% deletion pause threshold enforced as a hard block; this engine's own 2% ceiling enforced as a warning; matched enrollment moves netted out; unexplained row loss versus the last real push detected.
  • CSV integrity: a missing required column is now a hard load error, not a silent blank backfill; saves are all-or-nothing across the whole stack; pushes assert stack completeness before uploading.
  • Content generation fix: generated field "updates" (email, phone, etc.) are now re-rolled until they actually differ from the current value — previously ~62% of predicted users.updated (Contacts) events over 26 simulated weeks were silent no-ops.
  • Audit layer: JSON, Markdown, and history.jsonl reports per run, with scoped credential redaction, a preflight check that logs/ is writable before any work happens, and dry-run output capped at the 5 most recent directories per district.
  • Three schema additions: a Middle name column on students.csv, a Teacher 2 id column on sections.csv, and guardian contact columns -- all spec-optional, added because the real export had no mutable surface for three of the six event categories required. (The contact columns originally shipped as a standalone contacts.csv; corrected 2026-08-05, see below.)
  • Fixed (2026-08-03): corrected predicted event type names. The original build's EventType enum, following project brief §3, included contacts.created/contacts.updated/contacts.deleted and teachers.created — none of these are real Clever Events API wire events. Verified against Clever's live dev docs: contacts, students, teachers, and staff are all users objects in API v3.x; the only real events are users.*/sections.*, with role carried in the object's own roles node. EventType now contains only the six real wire events; a new EventSubject field on Change restores the role breakdown for reporting only (e.g. users.updated (Contacts)). Audit JSON schema bumped to v2.
  • Fixed (2026-08-05): contacts are rows on students.csv, not a separate file. The KNOWN BLOCKER previously recorded here was real: this engine wrote a standalone contacts.csv, which Clever's SFTP ingest has no concept of, so none of its predicted contact events would ever have fired. Confirmed against Clever's official SFTP Instructions, v2.1.1 (Dec 2025) on 2026-08-05 against the standard allowable-fields list, then fixed. Guardian contacts are now the seven unsuffixed Contact * columns on students.csv, with multiple contacts expressed as multiple rows per Student id (max 5); students.csv's key is (Student id, Contact sis id); every engine-created contact gets a minted, permanent Contact sis id so field edits surface as users.updated (Contacts); a student with no contacts keeps one blank-contact row and their first guardian fills it in place; student-level edits fan out across sibling rows; CsvStack.counts() reports distinct students plus a derived contacts count (a raw row count would have tripped the 25% scale gate mid-seed); the guardrail attributes contact-row deletes to contacts, not students; FileSpec.engine_added was removed, and every file in the now-six-file schema.ALL_SPECS was made required (later narrowed, see 0.2.1 below). Clever's SFTP specification (v2.2.0, fetched directly from Clever's internal tooling) requires only five files together -- schools, students, teachers, sections, enrollments -- and documents staff.csv as optional. New schema.OPTIONAL_FILES (currently just staff.csv) is wired into CsvStack.load/save and sftp_push._assert_stack_complete so its absence is tolerated only when the in-memory stack agrees it is genuinely empty -- a different mechanism from the old contacts.csv exception on purpose (that one existed because the engine owned the file; this one exists because Clever's spec says the file is optional).
